# 任务状态机与任务类型

## 状态（菜单，非强制路径）

```
待设计 → 设计中 → 待开发 → 开发中 → 待测试 → 测试中 → 通过
                                     ↘ 停滞（全程都可能，外部标注，原因可选）
```

- 每个"点"（设计点/开发点/测试点）执行时**先建任务记录文档**（`<点>/work.md`），再根据任务情况标注状态。
- 状态随执行进度更新，是 AI 记忆的载体；块级 `mode.md`/记录同样适用。

## 任务类型（创建点时标一次）

| 类型 | 组合 | 典型场景 |
|------|------|----------|
| 完整 | 设计+开发+测试 | 新功能 |
| 设计 | 纯设计 | 只出设计文档 |
| 实现 | 纯开发 | 设计已有，写码 |
| 验证 | 纯测试 | 回归/验收 |
| 修复 | 修复+验证 | 修 bug |
| 重构 | 开发+验证 | 内部结构调整 |

- 类型决定任务的**起点与路径子集**（如"实现"跳过设计态；"修复"走 待开发→待测试→通过）。
- 类型只在创建时标一次，后续状态按菜单自然走。

## 状态管理规则

1. **`<点>/work.md` 是唯一事实源**：AI 每操作一步就更新它。
2. **`project_plan.md` 功能清单状态只在收尾（通过/停滞）时回写一次**，其余状态一律看 work.md。
3. **开发自带自测**：自测通过即可标"通过"，不必等测试块。
4. **停滞**：被阻塞时标注，可附原因（外部标注为主）。
5. 块级看板（如 `develop/mode.md` 或 `index.md`）只是汇总视图，不替代 work.md。
