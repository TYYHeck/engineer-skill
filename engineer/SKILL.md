# Engineer · 树状三级项目文档协作技能（定稿 v2 · 瘦身方案 B）

轻量开发协作流程：**设计 → 开发 → 测试**，跨会话不断档。本技能维护 `engineer_doc/` 树状项目文档。

**核心原则（方案 B）**
- **位置交给文件夹**：层级 / 父子关系由 `engineer_doc/` 的目录结构天然表达，`Glob` 一次拿全树，不需要锚点编码位置。
- **状态交给节点头部**：每个节点文件头部用一行注释记录 `anchor / parent / status / active / path`，状态唯一真源在此，无中央索引、无双写。
- **快速取数靠 Grep**：取全图 = `Glob`（树）+ `Grep "status:"`（状态）；定位 / 读节 / 回弹全用 Grep 命中头部单行。
- **INDEX.md 可选**：仅作人工总览，AI 不依赖它判断状态。

## 一、文档树结构（全局 / 模块 / 子 三级）

```
<项目根>/
└── engineer_doc/
    ├── GLOBAL.md         # 层级0 全局大文档：分三块（设计/开发/测试），只列模块级概览
    ├── DISCUSS.md        # 层级0 同目录讨论文档：全局设计怎么得出的（来源/决策/被否方案）
    ├── auth/             # 层级1 模块（slug 命名，如 auth/）
    │   ├── MODULE.md     # 模块大文档：本模块具体分工设计（设计/开发/测试三节）
    │   ├── login/        # 层级2 功能
    │   │   └── PROGRESS.md # 功能进度文档：本功能设计/开发/测试三节
    │   └── register/
    │       └── PROGRESS.md
    └── order/
        └── MODULE.md
    # （可选）INDEX.md —— 人工总览，非 AI 状态真源，可不维护
```

### 三级职责

| 级别 | 载体 | 内容边界 |
|------|------|----------|
| **层级0 全局** | `GLOBAL.md` + `DISCUSS.md` | 只记**整个模块**的概览，不展开具体设计与分工 |
| **层级1 模块** | `<模块>/MODULE.md` | 记录该模块的**具体分工设计** |
| **层级2 子** | `<模块>/<功能>/PROGRESS.md` | 单个功能点的设计/进度/测试 |

**每级文档统一含三节**：`## 设计` / `## 开发` / `## 测试`。（模块级"设计"= 具体分工设计；子级"开发"= 进度记录。若某节过大允许拆同级独立文件，锚点仍指向该节点。）

### 节点文件头部（状态唯一真源，写在每个节点文件最上方）

每个节点文件第一行是注释头，单行、可被 Grep 直接命中：

```markdown
<!-- engineer_doc | anchor: G | parent: - | status: ~ | active: false | design: - | path: GLOBAL.md -->
<!-- engineer_doc | anchor: M:auth | parent: G | status: ~ | active: true | design: - | path: auth/MODULE.md -->
<!-- engineer_doc | anchor: F:auth.login | parent: M:auth | status: ~ | active: false | design: - | path: auth/login/PROGRESS.md -->
```

- `anchor`：节点唯一 ID（见第三节格式）。
- `parent`：父节点 anchor，用于回弹向上（GLOBAL 的 parent 为 `-`）。
- `status`：`[ ]` 待做 / `[~]` 进行中 / `[x]` 完成（状态唯一真源，只在此处）。
- `design`：`-` 待确认 / `confirmed` 已确认定稿。由 `eng-design` 在用户确认设计后写入 `confirmed`；`eng-develop` 开工闸门**据此判定设计是否已定稿**，保证**跨会话可验证**（不依赖对话记忆）。GLOBAL 此项恒为 `-`（顶层文档，闸门只作用于 MODULE/PROGRESS）。
- `active`：`true` 表示当前活跃节点（全树同时仅一个为 true），跨会话快速知道"现在干啥"。
- `path`：相对路径，便于 Grep 命中后直接 Read。

## 三、锚点系统（ID 用于 Grep 定位 + 节跳转）

### 3.1 锚点格式规范
```
结构：<level>:<slug>[.<subslug>][#<section>]
  level   : G 全局 | M 模块 | F 子功能
  section : design 设计 | dev 开发 | test 测试（可选，检索时按需追加）
示例：
  G                    全局
  G#design             全局·设计节
  M:auth               认证模块
  M:auth#design        认证模块·分工设计节
  F:auth.login         登录功能
  F:auth.login#test    登录功能·测试节
```
- 锚点 ID 是**稳定短句柄**，用于 Grep 精准命中（比路径更短、重命名文件夹后仍稳定）。
- 每个节点文件**头部**声明自身 `anchor`（不带 section）；section 在检索时按需追加。

### 3.2 锚点使用命令（token 最低，方案 B）

```
① 取全图（会话开头，2 调用，零双写）
   Glob  engineer_doc/**/*.md    → 树（位置，免费）
   Grep  "status:" engineer_doc/ → 所有节点状态（1 调用，新鲜，随项目增长比读大索引更省）
   # 可选：Grep "active: true" → 当前活跃节点

② 定位任意节点
   Grep  "<anchor>"  engineer_doc/  （递归）
   → 命中该节点头部单行，含 path + status，不读其他文件

③ 读某一块（精确读节）
   a. Grep 节点锚点 → 拿 path（如 auth/login/PROGRESS.md）
   b. Grep  "## 测试"  <path>  -A 50
   → 仅返回「测试」节，不加载整文件

④ 完成回弹更新状态（见 3.3）
```

### 3.3 状态回弹级联规则（读取流 + 回调流 + 两条硬规则）

**读取流（AI 怎么从头知道"我在哪、要改啥"）**
1. 会话开头：`Glob` 拿树 + `Grep "status:"` 拿状态（见 3.2①）。无需读任何索引全文件。
2. 已在某文件：读文件头部 `anchor/parent/status` → 知自身与父锚点。
3. 只想改某节点：`Grep "<anchor>" engineer_doc/`（递归）→ 命中头部单行，不全读。

**回调流（以"登录功能 `F:auth.login` 刚完成"为例，端到端）**
```
① 改自身状态（功能）
   Grep "F:auth.login" → 命中 auth/login/PROGRESS.md 头部
   Edit 该行 status: ~ → status: x

② 判是否「模块最后一子项」→ 回弹填模块状态（双条件门槛）
   Grep "parent: M:auth" engineer_doc/ → 取 auth 下所有子功能头部
   条件(a) 全部 status: x  且  条件(b) M:auth 的 MODULE.md §测试 用例全通过：
     → Edit M:auth 头部 status: ~ → x              # ⚠️ 填模块
     → （可选）同步 GLOBAL.md §开发 备注
   若任一不满足：停在 ~ 并标注剩余（如"剩余模块级测试 N 项未过"），结束。

③ 判是否「项目最后一模块」→ 回弹填项目状态
   Grep "parent: G" engineer_doc/ → 取所有模块头部
   若全部 status: x：
     → Edit G 头部（GLOBAL.md）status: ~ → x        # ⚠️ 填项目
   若未全 x：结束。
```

**⚠️ 两条硬性回弹规则**
- 某模块下**最后一个子功能**完成 **且** 该模块级测试（`MODULE.md §测试`）全通过 → 必须回弹填**该模块状态**（模块文件头部 `status` + 可选 GLOBAL 备注）。
- 项目中**最后一个模块**完成 → 必须回弹填**项目(全局)状态**（GLOBAL.md 头部 `status`）。

- 状态唯一真源 = **各节点文件头部**；回弹只改头部单行，无中央索引、无双写、不陈旧。
- 回弹逐级短路：没到"最后"就不往上走，避免无谓改动。全程 Grep/Edit 单行。

## 四、AI 快速回调（token 最低路径）

1. 会话开头：`Glob engineer_doc/**/*.md`（树）+ `Grep "status:" engineer_doc/`（状态）→ 全图，2 调用，零双写。
2. 要干活 → `Grep "<anchor>"` 命中头部拿 path → 只 Read 那一个节点文档（如 `auth/login/PROGRESS.md`），不读其他。
3. 跨节点取信息 → `Grep` 对应锚点 / 父锚点，再定点 Read 一个文件或一节。

对比旧 engineer（每次需读多个 references，典型 4-5 个才够用）：新方案"Glob+Grep 取全图 + 至多 1 个详情/节"，树还在，读取渐进式，且状态永远新鲜、无同步负担。

## 五、实时写入（讨论即落盘）

讨论中每确定一件事（新增模块 / 功能、改状态、记结论），**立刻**写回：
- 新增模块 → 建 `<模块>/MODULE.md`，头部写 `anchor: M:<slug> | parent: G | status: ~ | active: ... | design: -`
- 新增功能 → 建 `<模块>/<功能>/PROGRESS.md`，头部写 `anchor: F:<slug>.<sub> | parent: M:<slug> | status: ~ | design: -`
- 改状态 → **只改该节点文件头部 `status:` 单行**（唯一真源，无索引同步）
- 切活跃节点 → 把新节点头部 `active: true`、旧节点 `active: false`
- 模块内分工 → 写 `<模块>/MODULE.md`
- 功能进度 → 写 `<模块>/<功能>/PROGRESS.md`
- 全局设计依据 → 写 `DISCUSS.md`
- （可选）若维护了 INDEX.md 人工总览，可顺手同步，但不强制、AI 不依赖
层级文档用**追加**积累，不覆盖。

## 六、会话恢复与路由

- 若 `engineer_doc/` 存在：`Glob` 拿树 + `Grep "status:"` 拿状态 + `Grep "active: true"` 知当前焦点 → 恢复上下文。
- 若不存在：① 向用户确认**项目目标**（一句话；若对话已能推断可跳过）→ ② **确认开发方式 / 协作节奏**（见第八节：逐步开发还是一次性？是否走「提案→确认→定稿」讨论闭环？明确「确认定稿才开工」）→ ③ 用上方结构初始化 `engineer_doc/`（GLOBAL.md + DISCUSS.md + 首个模块及其 MODULE.md/PROGRESS.md，各带头部）→ 进入设计（由 `eng-design` 接管；git 跟进在此阶段确认，见第七节）。
- 按意图路由（统一用 Skill 工具加载子技能，三子技能平级 + 一个按需子技能）：
  - 设计类 → `eng-design`（写各级 `## 设计`；UI/交互设计作为内部分支，并在做 UI 设计时询问是否按需加载 `eng-ui-tooling`）
  - 开发类 → `eng-develop`（写各级 `## 开发` + 改头部 status + 触发级联回弹；受「确认定稿才开工」闸门约束）
  - 测试类 → `eng-test`（写各级 `## 测试` + 判定测试通过驱动回弹门槛）
  - UI 可视化/调试能力 → `eng-ui-tooling`（**按需**，仅 eng-design 在 UI 设计时询问启用后加载）
  - 用户直接点名某子技能 → 直接加载，不走路由

## 七、git 跟进（初始化时确认）

**由 `eng-design` 在设计阶段确认**（初始化不再单独问）：写 GLOBAL 设计背景时，`eng-design` 询问用户「是否用 git 全程跟进本项目？」，并说明：

- **git 的好处**
  - 版本可追溯：每次提交是一份可回看的快照，改了什么、为什么改都留痕。
  - 出错可回滚：引入 bug 或误删时能 `git revert` / `checkout` 回到上一个好状态。
  - 跨会话 / 多设备安全：文档与代码进度可推到远端，换机器、断会话不丢。
  - 进度可对照：把 `engineer_doc/` 提交进去，文档演进与代码改动一一对应。
- **不 git 的风险**
  - 进度只存在本地文档，误删 / 覆盖难恢复（无第二份）。
  - 无法定位「哪次改动引入了问题」，排查靠记忆。
  - 跨会话易丢上下文，尤其长项目多次中断后难接续。
  - 与他人协作时无合并 / 冲突解决基础。

**决策后行为**
- 若用户同意跟进：
  - 若目录无仓库：`git init`（必要时建远端并 `git remote add`）。
  - 在**每个有意义的检查点**提交（设计定稿 / 模块完成 / 重要功能落地 / 测试通过），提交信息带锚点（如 `[auth] 登录功能完成 F:auth.login`）。
  - 提交前确保 `engineer_doc/` 进展已写入。
  - 长会话或换设备前主动提示「要不要先提交一下？」。
- 若用户不同意：正常推进，不强制；但每次长段落工作后提醒「当前进度仅本地，建议手动备份」。

## 八、确认定稿才开工（防 AI 擅自开工）

借鉴 `perfect-design` 技能的协作哲学：**先问方向、出草稿、用确认门控、未确认就回到讨论**，杜绝 AI 不经确认直接动手写代码 / 改文件。

### 8.1 开发方式确认（初始化时，见第六节）
项目启动第一时间，除项目目标外必须确认**协作节奏**：
- **开发粒度**：逐步开发（小步快跑、做完一个确认一个）/ 一次性设计完再开发。
- **是否走讨论确认闭环**：设计 / 方案阶段是否走「提案 → 用户确认 / 调整 → 定稿」。
- **确认定稿才开工**：无论哪种粒度，**对应节点的 `## 设计` 未经用户明确确认定稿，`eng-develop` 不得开始任何实现**。

### 8.2 设计阶段确认闭环（eng-design 负责）
- 每产出一份设计（全局 / 模块 / 功能），向用户**呈现设计摘要 + 用多选题确认**（perfect-design 式「画完用多选题确认、未确认回到画→问」）。
- 用户未确认前不进入开发；要求调整则回到设计修改后再确认。

### 8.3 开发阶段闸门（eng-develop 负责）
- 开工前**必检**：对应 `PROGRESS` / `MODULE` 头部的 `design` 字段是否为 `confirmed`（即用户已确认定稿）。
- 未确认（`design: -`）→ **立即停止**，提示「该节点设计尚未定稿，请先确认（可加载 eng-design）」，不得擅自动工。
- 已确认（`design: confirmed`）→ 正常开发、实时落盘、完成后改状态回弹。

### 8.4 git 跟进并入设计阶段
- git 是否全程跟进不再在初始化单独问，改由 `eng-design` 在写 GLOBAL 设计背景时一并确认（利弊见第七节）。

## 九、定稿说明

- 本技能族（engineer hub + eng-design / eng-develop / eng-test 三平级子技能 + 按需加载的 eng-ui-tooling）已完整定稿并可用；核心新增「确认定稿才开工」闸门（见第八节）防 AI 擅自动工。
- 状态粒度：**保持三态** `[ ]` 待做 / `[~]` 进行中 / `[x]` 完成；阻塞 / 待审等写在文档正文（§开发 阻塞风险、§测试 备注），不进头部状态。
- 从零开始一个新项目：触发 engineer → 初始化 `engineer_doc/`（含 git 跟进询问）→ 按 `eng-design → eng-develop → eng-test` 推进，全程靠 Glob / Grep / 头部单行维护状态与回弹。

## 十、slug 命名规范

目录名 = slug，与锚点 ID 一一对应。

**模块（层级1）**
- 全小写英文，简短单数名词，如 `auth` / `order` / `payment`。
- 多词用短横：`user-profile`（不用驼峰、不用空格、不用中文）。
- 全局唯一；锚点 `M:<slug>`。

**功能（层级2，在模块下）**
- 全小写英文，动词或名词短语，如 `login` / `register` / `reset-password`。
- 模块内唯一；锚点 `F:<module>.<sub>`（如 `F:auth.login`）。
- 目录 `<模块>/<功能>/`，功能文档 `PROGRESS.md` 在其内。

**约定**
- 不用中文目录名（路径稳定、git 友好、锚点更短）。
- 名词优先作模块名，动词可作功能名。
- 重命名：目录改名后，对应锚点 ID / 头部 `anchor` / 父链 / MODULE 子任务表锚点须同步（锚点是稳定句柄，改名成本在此）。
- slug 与代码模块名可不一致，但建议尽量对应，便于对照。

## 十一、依赖与部署（完整性 · 可移植性）

本技能族是一个**整体**，迁移 / 部署时必须 5 个技能一起搬，缺一个路由会断：

| 技能 | 角色 | 是否必需 |
|------|------|----------|
| `engineer` | hub：结构 / 锚点 / 路由 / 闸门 | 必需 |
| `eng-design` | 设计子技能（平级） | 必需 |
| `eng-develop` | 开发子技能（平级） | 必需 |
| `eng-test` | 测试子技能（平级） | 必需 |
| `eng-ui-tooling` | UI 可视化 / 调试（按需加载） | 按需 |

**外部依赖**
- **`live-annotate`**：能力 A 的前端注入层资产（`assets/annotate.js` / `vite-annotate-plugin.js` / `references/data-ui-convention.md` / `references/inject-options.md`）**已内置**于 `eng-ui-tooling`，迁移时**无需**目标机共存 `live-annotate`。（仍可单独装 `live-annotate` 作独立技能用，但本族不依赖它。）
- **`perfect-design`**（软引用，概念借用）：确认闭环哲学来自它，不引用其文件，缺失也不影响功能。

**可移植性保证**
- 全族**零硬编码绝对路径**，所有引用用技能名 / 相对路径，换机器、改目录都能用。
- 状态唯一真源是 `engineer_doc/` 节点头部，不依赖任何外部索引文件，搬项目文档即可带走全部进度与状态。
- 本技能族自带文件**不含任何 `.git` 版本库**；若你自行把项目 git 化，请在目标处 `git init`，不要把其它目录的旧 `.git` 带入（旧版仓库会让人误 `checkout` 回被推翻的方案）。
